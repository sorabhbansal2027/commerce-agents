Identity & Access

  • OAuth 2.0 + PKCE for web channels
  • SAML 2.0 for enterprise SSO
  • API keys for agent-to-agent (UCP)
  • Named Credentials in Salesforce Org
  • RBAC: buyer · merchant · admin · agent
  • JWT expiry: 1h access, 30d refresh
  • MFA enforced for merchant role
🛡️

AI Safety Controls

  • Provenance gate: only host-authored data can trigger writes
  • 3rd-party content (product descriptions) fenced in data blocks — never instruction-level
  • Write cap: merchant changes ≤ N items per session
  • Checkout: status always "pending" — no charge
  • Tool descriptions define when tools apply
  • Skill descriptions define request class only — no sample utterances
  • Host approval required before any state change applies
📋

Audit & Compliance

  • Every API request logged: actor, action, timestamp, IP, tenant
  • Every agent tool call logged: tool name, args, result hash
  • Every merchant write logged: before/after state diff
  • WORM storage: 3-year retention, immutable
  • PII pseudonymised in logs (buyer_id not email)
  • GDPR right-to-erasure: memory store purge API
  • SOC 2 controls mapped to audit events
🔒

Encryption

  • TLS 1.3 on all external channels
  • mTLS for service-to-service (gateway → platform → backend)
  • AES-256-GCM for PII at rest (memory store)
  • Field-level encryption on buyer profile fields
  • Secrets in AWS Secrets Manager / Vault
  • API keys: env var injection at runtime (never in code)
  • Anthropic API key: scoped per-tenant
🌐

Network Security

  • WAF: OWASP Core Rule Set 3.x
  • DDoS: Cloudflare / AWS Shield Standard
  • VPC isolation: platform zone not publicly routable
  • Security groups: ingress only from API Gateway
  • Egress: only to Anthropic API + Salesforce endpoints
  • No direct DB access from channels
  • Rate limit: 1000 req/min per tenant, 100 req/min per user
🔑

Secrets Management

  • ANTHROPIC_API_KEY — AWS Secrets Manager
  • GEMINI_API_KEY — AWS Secrets Manager
  • Salesforce Named Credentials — SF Org vault
  • Database credentials — injected at container start
  • Rotation policy: 90 days for API keys
  • Zero secrets in code, git history, or logs
  • .env.example in repo — .env never committed

Integration Patterns & Protocols
Four distinct integration patterns serve different consumer types — from human web users to autonomous AI procurement agents — all backed by the same commerce platform.
🌐

Pattern 1 — UCP (Protocol Standard)

Google Standard Zero Config Any AI Vendor

Any UCP-aware AI agent discovers the full store capability from a single URL. No vendor-specific SDK or custom adapter needed. Gemini, GPT, custom bots all use the same contract.

1

Discovery

GET /.well-known/ucp → JSON manifest with capabilities, endpoints, payment handlers

2

Tool Generation

Agent auto-generates function declarations from capability block — search, get, checkout

3

Shop & Checkout

GET /ucp/products?q=&max_price= → results → POST /ucp/checkout-sessions → pending

🔧

Pattern 2 — MCP (Tool + UI)

Anthropic Standard SEP-1865 In-Chat UI

Claude hosts connect to the MCP server to get structured tools. With SEP-1865 MCP Apps, tool results carry a ui:// resource URI — the host renders interactive HTML alongside the chat response.

1

Tool Call

Claude calls search_products_ui — result includes _meta.ui.resourceUri: "ui://storefront/product-grid"

2

Resource Fetch

Host fetches the resource, renders sandboxed HTML iframe beside the chat message

3

postMessage Bridge

User clicks "Add to cart" in iframe → mcp/call_tool fires back to host → tool executes without new turn

⚡

Pattern 3 — Salesforce LWC (Apex Callout)

Embedded Named Credential Bedrock Option

Lightning Web Components embedded in Salesforce pages call Apex controllers, which make authenticated HTTP callouts to the Railway commerce API. Response streamed back via SSE or HTTP.

1

LWC → Apex

@wire or imperative call to CommerceAgentController.sendMessage()

2

Apex → Railway

HTTP callout via Named Credential (callout:Commerce_Agent_API/api/shopping-agent/) — no API key in code

3

Response → UI

Agent response streams back; LWC renders message in chat panel with generative components

🖥️

Pattern 4 — Next.js Headless (SSE Stream)

Buyer Portal Merchant Dashboard Generative UI

Next.js App Router apps connect to the FastAPI backend via SSE streaming. The agent emits ui events in addition to text — the frontend renders matching React components (VenueMap, MetricsCard, etc.).

1

Chat.tsx → /api/shopping-agent/

POST with session_id + message → EventSource opens SSE stream

2

Agent executes tools

Backend runs turn loop: grounding → Claude → tool calls → enrichment → streaming events

3

Generative UI rendered

ui events carry JSON payload; frontend maps to React components via components/generative/index.tsx

Cost Governance

  • Token usage logged per request + tenant
  • Prompt caching: ~90% cache hit = 5-min TTL
  • Static prompt bytes never change → always cached
  • Alert: daily spend > $X per tenant
  • Turn limit: max 20 tool calls per session
  • Model: claude-sonnet (fast) default; opus gated
  • Bedrock Reserved Capacity for predictable spend
🔬

AI Quality Gates

  • scripts/check.py: system.md matches derived manifest
  • scripts/smoke_chat.py: end-to-end chat round-trip
  • Evals: contract tests per vertical (test_contract.py)
  • Regression: tool call coverage checked in CI
  • Skill descriptions reviewed on every SKILL.md change
  • Prompt fences: third-party content never reaches instruction level
  • ruff check + ruff format on every PR
🏢

Multi-Tenancy Model

  • tenant_id bound at session creation (session middleware)
  • All backend calls scoped by tenant_id
  • Memory store keyed by tenant + buyer
  • Separate Salesforce Named Credentials per tenant
  • Separate API keys per tenant (Anthropic + Gemini)
  • Vertical = logical tenant in examples/ structure
  • Shared agent code; isolated data + config per tenant
